## Executive finding

The main problem is not missing documentation quantity. It is that **product authority, implementation status and terminology are out of sync**. Several capabilities are partially scaffolded in code and described as if complete, while the owner has now made new decisions that differ from the published specification. Avoid starting another wholesale rewrite. Reconcile the existing architecture with a small set of accepted ADRs, then implement bounded vertical changes.

## D. Recommended implementation order (do not start all at once)

1. **Documentation/authority freeze**: merge glossary + ADRs after review; amend AGENTS; reconcile SPEC/ROADMAP/TEACHERS; tie open GitHub issues to decisions. No gameplay change in this PR.
2. **Engine evidence seam**: save migration and weighted skill mastery, question format/difficulty semantics, deterministic mathematical validation, scenario tests. Preserve compatibility for the existing study consumer.
3. **Persistence and course UI**: exact active-run save/resume, course in settings, inactive geography, generic mastered-skill dashboard and explainer navigation.
4. **Regional vertical completion**: design owner-approved story boss milestone, continue/endless and PB; validate with one region before applying to all five.
5. **Thunderdome**: Exhibition topic selection + weighted encounter director + fixed floor; then approved Boss Rush after testable unlock and fee simulation.
6. **Progression/economy**: three character XP trees, account accolades, Bazaar/merchants, score/assist effects, Raider Attention; simulate economy and XP for early and advanced users.
7. **AA SL content/polish gate**: five zones, all approved skill coverage, representative structures, explainers signed off and linked, art/voice consistency, classroom test. Only then expand other courses.

## E. Required proof, not just a plan

- CI green on existing Godot headless tests + answer checker + seed sweep; assess the impact of test duration and run known-good seeds in staged PRs.
- New mathematical tests for course filtering, per-skill evidence, skills in multi-skill questions, weighted asymmetric updates, 1-7 stages and no unexplained mastery spikes.
- Save migration and pause/resume property tests including crash/relaunch mid-question, one-run invariant, combat modifier persistence, earned Scrap safety and unlocked milestone safety.
- Reproducible question-selection tests: floor behavior by mode, random weights after a miniboss, no guaranteed topic rotation, topic breadth constraints and state-driven adaptive difficulty.
- UX tests for syllabus course switching from settings, invisible interaction on ineligible locations, dashboard deep links, bounty board restricted to hub, no intrusive mid-run educational popup, and arcade PB celebration.
- Reviewer signoff on mathematical correctness, age-appropriate narration and AA SL explainer coverage, with no assumption that 'mapped' equals 'completed'.

## Conclusion

**Do not rewrite the game now.** First review these decisions and put agents under the agreed scope rules, then systematically close observable gaps with tests. The biggest blocker is governance/semantic drift, followed by mastery evidence and run persistence. New art/content can proceed on separate approved issues without making unrelated system changes.


## F. Owner interview continuation: boss/encounter audit addendum (2026-11-21)

The earlier audit predated a further design discussion. Three new accepted records are **ADR-0005 (encounter/status framework), ADR-0006 (event-driven narrative villains), ADR-0007 (modifiers and inventory scope)**. They supersede any assumption that adding new named voice-heavy boss characters solves replayability.

**New audit requirements:**

1. **Verify actual content count**. A later prior public-source inspection reported **13 boss + 13 miniboss definitions** and heavy Functions concentration (8 pairs), but this handoff could not re-clone the repository. Compare latest `bosses.json` and actual Godot scenes/assets; classify *defined vs implemented vs voiced-if-needed vs tested vs polished*. Follow `docs/implementation/ENCOUNTER-AND-BOSS-AUDIT.md`.
2. **Existing code structure vs desired:** inspect whether the existing repeating mile boss loop, journey's Explore/Puzzle presentation and boss definitions can map to one shared combat/hazard/repair runtime. Do not treat all current bosses as one-time regional finales.
3. **Narrative flags:** confirm presence/absence of villain encounter/escape/final-victory flags, conditional phases, branch outcomes and Thunderdome roster unlocks. If missing, propose a minimal event model, not a custom quest system per boss.
4. **Status effect support:** confirm existing effects, save schema, tick timing (now **per resolved maths question**), stack rules, caps, cures and resistances. Test interruption/pause/resume and multi-phase outcomes.
5. **Content and VO:** assess whether existing antagonists are sufficiently unlikeable/interesting, whether survival and repair encounters truly differ beyond presentation, and where missing art/voiced scenes block polish. **Do not assume more voice lines is always better.**
6. **Inventory scope:** owner specifically *declined* an automatic stash/run-inventory/quick-bar split. Do not treat existing inventory limits as a reason to implement a new subsystem until a concrete playtest need is established.

**Important nuance:** The owner accepted mathematical and narrative progression as distinct tracks, approximately three story beats per region, and the possibility of strong players reaching story milestones with less maths grinding. The *exact* final-boss mapping, math readiness gate and triggering values remain **OPEN**. The earlier D-02 question is now narrower: map the existing Godot floors/miles and existing bosses to this agreed event-driven story architecture.
